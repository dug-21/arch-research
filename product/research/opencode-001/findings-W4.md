# W4 — Model assignment, repository identity and Collective sharing

**Evidence date** 2026-11-26. **Directional source audit.** OpenCode v2.4.1 (`6f05140`) and Unimatrix `e2194af8c32c1fca8767c4e61a0667be4fd7566c`. The required behaviors are deliberate assignment for parent and delegated tasks, explicit and attributable fallback, continuous observation and scoped memory for both interactive and programmed runs. The current OpenCode adapter's coverage is evidence about one implementation. Runtime behavior, isolation and migration remain to be demonstrated.

## Model selection has three boundaries

| Boundary | Pinned source behavior | Consequence |
| --- | --- | --- |
| **Admission** | The v2 prompt endpoint admits text, attachments, metadata, delivery and resume control. It has no request-level model field. The native prompt hook runs during admission, while the runner resolves the model later. | Pass the model at session creation, or explicitly switch before submitting to an owned idle session. Put the routing reason in structured application metadata as telemetry, with the decision enforced through the model field. |
| **Session** | Session creation and `session.switchModel` accept a provider/model/variant reference. The selected model applies to subsequent provider turns. The headless CLI applies its agent/model choice by switching the session before prompting. At resolution, the stored session model wins, then an available agent model, then the resolver's default/first eligible text runtime. An explicitly selected unavailable model errors. | A configured agent model works as a default and does not replace an existing explicit selection. A switch followed by prompt admission consists of two operations, so task-specific routing needs owned sessions or serialized exclusive writes. An attached TUI, resumed work or queued child notifications can otherwise share that mutable choice. |
| **Model call** | `experimental.model.resolve` receives the selected reference with session, agent and request kind. It can replace only the model or variant inside the already-selected provider. Core fails a cross-provider rewrite. Context hooks see the effective reference after resolution. Provider connection resolution independently looks up the integration's active credential. | Use the hook for experimental within-provider choices and use request telemetry to audit actual selection. Assign OpenAI versus Claude Agent at session setup. An `openai/<model>` assignment alone does not pin the ChatGPT or API-key credential. Record the expected credential class and validate the effective connection, especially where more than one is configured. |

**Native delegation.** New children use explicit `subagent.model` input first, then the child agent's configured model, then the parent's stored model. The parent runner's resolved default is not read at this point. A resumed child keeps its existing model unless the caller supplies a model or switches to an agent with a configured model. The native tool validates an explicit chat model and variant, checks role permission and existing child lineage, then admits the child prompt. Thus an agent's fixed model configuration alone is insufficient as an enforceable routing policy when the model can pass an override. A location plugin's typed `tool.execute.before` hook is a candidate for controlling the native subagent's model input. The built-in plugin already uses that hook to normalize empty model/session arguments. Prove the override handling on both provider paths and inspect any other path that can create children. [Pinned child model and launch](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/tool/plugin/subagent.ts#L127-L217) · [Pinned child input normalization](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/tool/plugin/subagent.ts#L229-L238) · [Tool hook invocation](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/tool.ts#L161-L171)

**SDK delegation.** An external orchestrator can create a child with `parentID`, explicit agent and model, then prompt it. The child takes the parent's location and inherits metadata/permissions unless supplied. The method accepts a caller-provided session ID and returns an existing session on an ID collision, which supports stable request correlation but requires verifying an existing session's binding before reusing it. Using this route leaves native children and other creation paths to be governed explicitly. [Pinned session create API](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/protocol/src/groups/session.ts#L166-L180) · [Pinned create semantics](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/session.ts#L291-L321)

**Retry and failover.** The runner's retry contract modifies permission to retry and delay. It has no substitute provider field. Model selection fallback when a session has no explicit model is separate from recovery after a provider rejects an invocation. ChatGPT token-sharing disables retries for selected entitlement/quota errors. Claude Agent's multi-directory option can select another account on certain limits before visible output, adding a separate provider-local behavior. Keep that off for the initial validation and make cross-provider fallback a fresh, explicitly authorized dispatch from a known continuation state. Preserve an attempt ID, prior actual model, rejection class, whether side effects occurred, and fallback credential class. Do not replay completed tool effects or promote a partial answer into an independent successful run. Route title, compaction and generation calls deliberately too. The pinned title path can choose an auxiliary agent/small model, so observing only visible conversation turns misses some consumption and possible memory disclosure. ## Repository placement and memory identity

Treat host location and authorized memory binding as independent inputs. OpenCode stores project ID, authoritative location and working subpath on creation. The location uses a directory and optional workspace identity. Its project discovery resolves the worktree and canonical main checkout through Git and typically derives the project ID from normalized origin **host and path**. A cached ID, root commit or global ID is a fallback. A common repository origin can thus join clones even when their checkout paths differ. A remote URL and root commit identify lineage or configuration and do not establish authorization for memory access. A plugin should get placement from the running session server and resolve the explicit Unimatrix binding there. [OpenCode project discovery](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/project.ts#L309-L382) · [OpenCode location](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/location.ts) · [Session binding](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/session.ts#L291-L321)

| Case | OpenCode placement | Unimatrix store and implication |
| --- | --- | --- |
| Subdirectory | Git resolves the project root and keeps a session subpath. | Ordinary local root discovery ascends to `.git`. An explicit `--project-dir` overrides the starting identity and canonicalizes that directory, resolving a worktree marker at that directory only. Pass a verified repository root to an explicit override. |
| Linked worktree | Project canonical path usually points to the main checkout, while execution has its own workspace/directory. | A standard linked worktree's `.git` pointer resolves back to the main checkout path, sharing the same local store. Preserve worktree provenance on events. A separately initialized storage checkout deserves its own binding test. |
| Clone and move | Same normalized remote can lead to the same project ID across clones. | Distinct canonical clone paths are distinct local stores. Moving a checkout can change the local path hash. Use explicit, authorized bindings if intentional memory continuity across clones or hosts is required. |
| Remote or remote-managed server | Authority follows the actual session server and location. A server or worktree transition can change the directory even when the project looks familiar. | Path hashes are host-local. An operator-registered Unimatrix cloud slug or explicit approved project binding addresses portable identity. Record moves as placement changes and recheck binding before observing or injecting. |
| Non-Git or unresolved | Model/session execution can have a valid location without a trustworthy repository mapping. | Unimatrix's unbound local discovery uses cwd. An adapter can allow isolated local behavior when explicitly configured, or suspend automatic memory until binding is known. Infer no sharing from a global OpenCode ID. |

[Pinned Unimatrix local project resolution](https://github.com/dug-21/unimatrix/blob/e2194af8c32c1fca8767c4e61a0667be4fd7566c/crates/unimatrix-engine/src/project.rs#L34-L135) · [Pinned Unimatrix project slugs and routing](https://github.com/dug-21/unimatrix/blob/e2194af8c32c1fca8767c4e61a0667be4fd7566c/README.md)

The cloud service routes observation and MCP by a registered slug into separate databases, vector indexes and analytics. Its attach bundle provides server-composed URLs for both paths. The legacy bearer spans slugs. The pinned revision also offers revocable slug-bound headless bundles. Their `read` mode permits MCP read and search but rejects observation. Their `read-write` mode permits observation and additionally grants Write and SessionWrite. An observation adapter therefore needs a protected writer credential or a narrower capability to be added if the owner wants a credential that can observe without granting knowledge mutation. The host can disable the legacy bearer once clients have migrated. The trace should prove both operations share the registered binding and no process accidentally reaches an unscoped store. [Pinned Unimatrix cloud deployment and bundle documentation](https://github.com/dug-21/unimatrix/blob/e2194af8c32c1fca8767c4e61a0667be4fd7566c/README.md) · [Scoped access modes](https://github.com/dug-21/unimatrix/blob/e2194af8c32c1fca8767c4e61a0667be4fd7566c/docs/client-setup.md#headless-automation-access)

## Collective and cross-repository knowledge

Both the arch-research projection and the checked Unimatrix revision record adoption of release 0.3.0 with the same content digest, and their projected operating contracts have identical bytes. The registry identifies the two Programs independently. The operating contract carries deliberately classified baseline material and owner-authorized direction. It describes immutable release identity and explicit adoption, and excludes private decisions, evidence transcripts and review paths from the published payload. The baseline carries no credentials and grants no authority of its own. A Program ID in this projection identifies a participant, while a verified repository binding controls which Unimatrix store receives events or serves retrieval. [Arch-research participation surface](../../../.collective/README.md) · [Adoption record](../../../.collective/ADOPTED.yaml) · [Operating contract](../../../.collective/contract/CONTRACT.md) · [Unimatrix adoption](https://github.com/dug-21/unimatrix/blob/e2194af8c32c1fca8767c4e61a0667be4fd7566c/.collective/ADOPTED.yaml)

The Collective repository's `main` tree observed on November 26 contains versioned baseline releases, a registry, release controls and tooling for admission, delivery, projection and adoption observation. The product vision places durable knowledge and evidence context with Unimatrix and assigns the Collective the participation and governance boundary. This supports a potential publication and adoption pattern. The inspected contract and inventory establish no runtime interface for searching another Program's Unimatrix store. The tree inspection and vision read were read-only and narrower than an implementation audit of every Collective tool. [Collective repository](https://github.com/dug-21/collective) · [Accepted baseline directory](https://github.com/dug-21/collective/tree/main/baseline/releases/0.3.0)

**Candidate extension.** Adapt the Collective publication pattern to a deliberately shared knowledge lane. A repository exports an owner-approved, classified entry with provenance, immutable revision, intended recipients, and explicit receiver acceptance. Imports carry source identity and revision and need a way to recognize supersession or withdrawal. A first validation can use one harmless separately published canary and confirm that only that canary crosses the boundary. Keep private observations, automated learning inputs, transcripts, embeddings of private texts and credentials in the originating project. Sharing an adopted instruction through the Collective and importing an advisory retrieval entry have different authority semantics and should remain distinguishable at consumption. This is a candidate design derived from the contract, with cross-repository retrieval behavior unverified.

## Ranked integration shapes

| Rank | Shape | Implementation and upgrade exposure | Routing and memory control |
| --- | --- | --- | --- |
| **1 — Assemble** | Server-side OpenCode v2 memory adapter plus an SDK coordinator that supplies explicit models to owned parent and child sessions. | Uses public session creation/prompt APIs and typed server hooks. Needs an OpenCode-side adapter for capture and injection, plus a repository binding shared by observe and MCP. Provider-specific injection tests remain essential. | Strong for coordinator-owned tasks. Govern native child overrides on the same server when enabled. Preserve a uniform repository binding and observe through lifecycle hooks. |
| **2 — Extend** | One server plugin for interactive OpenCode with configured default agents, a controlled primary-session switch and a native subagent input policy. | Smaller visible surface for daily TUI use, but session mutation and plugin order couple routing to concurrent admission. The experimental request hook adds same-provider flexibility only. | Good for advisory defaults. Requires proof that policy covers alternate delegation/SDK routes and that switching cannot race another authorized turn in the same session. |
| **3 — Park** | External SDK and subscriber only, or provider-level interception, with no memory plugin. | Narrow client integration, but the volatile event stream needs recovery and observer code cannot synchronously shape arbitrary native requests. Provider wire interception misses the Claude Agent subprocess boundary. | Suitable for a restricted SDK-only workflow. Insufficient for native interactive/child context injection and complete lifecycle capture without additional host integration. |

**Next discriminating test.** In two repositories, create one primary session and explicit native/SDK child per provider route. Exercise mismatched agent selection, caller-supplied unauthorized model, invalid or unavailable model, a quota-class failure and a deliberate paid-fallback boundary. Trace the selected credential class and effective model on primary, child and compaction. Run from root, linked worktree and fresh clone and move or reconnect a session across placements. Assert that observe and retrieval bind together and that each private canary stays within its approved repository. Add a published canary only after both isolation controls pass.
