# W1 — OpenCode v2 releases, credentials and provider behavior

**Evidence date** 2026-11-26. **Directional.** Source inspected at the immutable OpenCode v2.4.1 tag (`6f05140`). Hosted documentation and release notes were checked separately. No executable was installed, no account was connected, and no billing or runtime assertion is treated as demonstrated.

## Release selection

The official changelog lists **v2.4.2** on November 26. Its changes include a GPT-6.2 system prompt update and session moves that include subagents. This workstream pins **v2.4.1** (November 23), shared with the other source audits. The repository's `/releases/latest` URL resolved to v1.19.6 during the survey, and the legacy npm package `opencode-ai@latest` also returned 1.19.6. The v2 install page instead lists `@opencode/cli`, the `opencode-v2` Homebrew tap formula, and the v2 installer. Both `@opencode/cli` and `@opencode/plugin` manifests at the pinned tag declare 2.4.1. This establishes which source contracts were compared. It does not establish dist-tag propagation across registries or the version of any binary on the owner's machine. Record the installed CLI, plugin dependency, Claude Code binary, Unimatrix revision, and actual model catalog before the trial. ## What the actual code means for the harness

### ChatGPT route

The v2.4.1 `chatgpt.ts` source checks OAuth state and client identity, verifies the ID token, and requires `chatgpt.tokens.use.direct` before accepting a usable connection. It configures the HTTP Responses route, sets session/thread affinity headers, filters models by `models.dev` subscription catalog or a fallback allowlist, and selects summary-based compaction. The transform disables the reasoning mode marked `pro` on this route, which is distinct from whether the account has a ChatGPT Pro subscription. Several sharing-specific refusal codes, including quota and ineligibility, explicitly disable automatic retries. A visible model ID or HTTP 429 alone cannot establish account entitlement or reset time. [Pinned authorization](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/plugin/provider/chatgpt.ts#L105-L213) · [Pinned session and model transforms](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/plugin/provider/chatgpt.ts#L277-L347) · [OpenAI error semantics](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery)

OpenAI's November 4 SIWC terms distinguish a user-controlled client from a subscription-backed service. For plan use they require a user-controlled runtime, authorization for that user's work and express consent for background use, and limit consumption to the connected application. They disallow pooling or routing one user's entitlement to another user. A single-user OpenCode extension should keep OpenCode's credential path intact. A separate multi-user application or general-purpose gateway needs its own supported authentication and billing design. [SIWC terms](https://openai.com/policies/sign-in-with-chatgpt-terms/) · [Open-source integration guide](https://developers.openai.com/siwc/quickstart)

### Claude Agent route

The v2.4.1 source passes the configured executable, a subprocess spawn implementation, the OpenCode session working directory, requested model and effort, and the OpenCode-derived system prompt to the SDK. It sets `settingSources: []`, `disableAllHooks: true`, `strictMcpConfig: true`, and empty native tool and skill lists. Normal session creation explicitly installs OpenCode's own tool callbacks and an MCP server named `opencode`. The callbacks correlate the Claude tool ID with the pending OpenCode action and return richer results. The passed MCP tool names and session options are direct evidence of the intended bridge. The distinction between disabled user hooks and working SDK callbacks should be exercised on a real signed-in binary. [Pinned query options](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/plugin/provider/claude-agent/claude/query-options.ts#L85-L139) · [Pinned tool server](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/plugin/provider/claude-agent/tools/server.ts) · [Pinned callbacks](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/plugin/provider/claude-agent/tools/hooks.ts)

This directly changes the expectation for Unimatrix. The user's ordinary Claude Code project settings and hooks are excluded. A Claude call to an exposed Unimatrix tool would be brokered through OpenCode's configured tool surface, conditional on configuration and tool permission. Continuous observation, automatic retrieval at prompt or child start, and compaction behavior each need independent evidence. By design, OpenCode owns compaction, subagents, policy around brokered tools and the authoritative history. Claude Agent maintains a subordinate Claude transcript. On switching to Claude, conversation history that Claude has not seen can enter as a checkpoint. The provider spec describes context-hook mutations as inputs to that reconciliation. Claude Code's actual Anthropic requests do not run OpenCode's HTTP hooks, so request-level policy or evidence must have a placement appropriate to that boundary. An unoffered tool attempt can remain inside Claude and be absent from the host transcript. [Pinned provider spec](https://github.com/anomalyco/opencode/blob/v2.4.1/specs/v2/claude-agent-provider.md) · [Pinned Claude language model bridge](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/plugin/provider/claude-agent/language-model/claude-agent-language-model.ts)

Claude Agent can map an explicitly configured `apiKey`, `authToken`, or `baseURL` to the subprocess environment. The launcher also inherits the host environment. A successful test while these are configured cannot establish subscription attribution. OpenCode's provider passes the `opencode` entrypoint label, and the spec reports no equivalent to the native Claude usage and limit-management interface. For a dependable comparison record the effective authentication class and use vendor-side evidence. Keep credential and quota boundaries external to the router's model aliases. [Pinned connection and launch options](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/plugin/provider/claude-agent/claude/query-options.ts#L12-L103) · [Pinned provider spec](https://github.com/anomalyco/opencode/blob/v2.4.1/specs/v2/claude-agent-provider.md)

Anthropic distinguishes personal sign-in through an unmodified Claude Code binary from OAuth credentials being gathered, stored, intermediated, or used on behalf of customers. Anthropic directs developers integrating Claude into products toward API keys or supported cloud credentials, and specifies commercial terms and conditions for hosting the published binary. The OpenCode release and source are evidence of a local delegated execution mechanism. They grant no blanket permission for a hosted or multi-user platform. Also distinguish the source's `configDir` account fallback from an explicit owner routing policy. Its behavior should remain outside the first trial so account attribution is unambiguous. [Anthropic usage and hosting terms](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use) · [Anthropic subscription versus API metering](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) · [Pinned account behavior](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/plugin/provider/claude-agent/claude/accounts.ts)

## Interactive versus programmed use

The CLI docs establish both TUI and `opencode run`, normally backed by a per-user shared server that owns integrations, permissions and tool execution. Desktop and terminal model selection do not verify that an SDK prompt uses the same server, account, project and provider. A programmed run attached to another server may see a different login or no locally installed Claude binary. Validate the same explicit provider/model and connected account once through the TUI and once via an SDK or headless call, bound to the same known server. Capture the resolved model, route, tool event, repository scope and plan debit. Then separately test an unavailable connection, missing Claude binary or denied plan consent. An expected failure must remain attributable rather than transparently shifting to paid credentials. [CLI and shared service docs](https://opencode.ai/docs/cli/) · [OpenCode API docs](https://opencode.ai/docs/api/) · [Pinned Claude provider spec](https://github.com/anomalyco/opencode/blob/v2.4.1/specs/v2/claude-agent-provider.md)

## Directional decision and discriminating trial

**Assemble** OpenCode as the candidate owner of model routing, sessions and tool policy, with independently testable provider adapters. The critical unknown for a primary-harness decision is the **provider-specific control boundary**. ChatGPT goes through OpenCode's Responses driver. Claude Agent delegates inference through an SDK subprocess and remaps tools and messages. A useful trial must verify context delivery and observation on each route, including a delegated child and compaction. Compare against the native Claude Code baseline where the owner's normal hooks run. Start with a single personally controlled login per advertised plan, select the routes explicitly, check each provider dashboard, and separately exercise any paid key or fallback behavior. No result here establishes that the shipped Unimatrix adapter covers those workflows.
