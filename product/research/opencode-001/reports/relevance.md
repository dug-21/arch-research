# opencode-001 synthesis relevance review

**ALIGNED.** The synthesis answers the remote harness decision with a bounded, one-server-per-container pilot and workstation-only UI. It tests routing, observable learning, model-effective memory and repository isolation against the current Claude Code workflow. Before any pilot sends real repository content to a public provider, require an explicit, auditable egress decision that covers parent, child and auxiliary calls. Defer cross-harness portability until the two-container proof shows the adapter can preserve the workflow.

The report and curator position #402 answer the broader goal in #242 and the immediate capability in #245. The determining evidence is provider-effective context delivery and downstream use of observations, with explicit model selection under #244. The pilot preserves existing VS Code access, pairs each remote endpoint independently, and binds server and checkout to the same authorized Unimatrix slug for capture and retrieval. The two-repository checks exercise a real protocol and blocked gate, reconnect, private memory canaries and remote execution markers. Desktop status and the separate console remain implementation choices subordinate to that proof. [Scope](../SCOPE.md) · [Synthesis](../REPORT.md) · [Owner's remote-container requirement](https://github.com/dug-21/arch-research/issues/77#issuecomment-7181688849)

The sovereign-goal NFRs cover owned compute (#7), operation through vendor or network loss (#8), sensitive-code egress (#9), and future multi-machine operation (#10). Existing remote containers satisfy the owner's placement requirement for this pilot. Ownership, budget and operation without vendors remain separate proof questions under #242. The report's account attribution and redaction controls should be complemented by an explicit egress decision before real content is sent to each public route. Exercise denial with synthetic sensitive content and include tool results, injected memories and auxiliary calls. This extends the proof for #244 rather than requiring a new capability.

**Step-function opportunity — defer and record.** A harness-neutral protocol, routing and memory contract could make an entire delegated workflow movable between provider-eligible OpenCode sessions and a local Claude Code comparison or other eligible harness while retaining durable gate, policy and memory provenance. That would make a host change or vendor outage a bounded placement decision instead of a workflow rebuild. It would cost a second maintained adapter, a stable interchange contract and additional replay, egress and authorization tests. Revisit after the staged pilot establishes a real behavioral baseline and identifies which lifecycle and memory semantics are portable. At that point a separately scoped portability capability would be warranted if changing hosts still strands a meaningful class of work.
