# opencode-001 — OpenCode v2 as a remote development harness

**Workflow** `wf-v0.26-69-g63e2578`
**Verdict — ASSEMBLE a bounded pilot.** Use OpenCode Desktop for project switching, chat and files, with one OpenCode server inside each existing remote development container. ## Integration order

1. **Assemble the server adapter with an SDK coordinator.** Reuse OpenCode's host and session APIs (Unimatrix #252), the pinned v2 extension surfaces, and Unimatrix's project-scoped transport where it can carry the required fields. Reuse the native adapter candidate (#393). Build the missing synchronous memory-application and durable observation reconciliation inside the server boundary. Keep the coordinator's model and gate decisions explicit. This is the leading fit for both interactive access and controlled protocol runs.
2. **Extend with a plugin-led interactive path if useful.** Configured agents and native subagent input hooks can simplify ad hoc work. This path depends more heavily on plugin order and ownership of mutable session state. Prove model admission and the supported child entry points before applying it to governed runs.
3. **Park an SDK observer alone and a host-wide server.** An external subscriber can observe and control its own requests, while native request injection needs an in-process seam. A host-wide server would need independently verified container-aware placement and a different filesystem and credential boundary.

The workstation is the display and control surface. Repository files, session state, plugins, provider runtime and tool execution belong to the selected remote container. Preserve existing VS Code remote access. Reach distinct authenticated container endpoints through private forwarding or SSH that enters the container environment. Provision agents, commands, skills, protocol launchers and adapter configuration from the shared profile. Keep project overrides and approval bindings explicit. Keep provider credentials and the slug-scoped observation credential in the execution environment. At the audited pin, observation requires a credential that also grants write. Expose a separate read credential to model-facing retrieval and reserve knowledge mutation for the curator role. Desktop pairing is separate from provider login. ## Staged validated follow-on — remote OpenCode harness trial

**Status** staged. **Target** routing-capable agentic harness (#245), using routing contract #244 and adapter candidate #393. **Confidence required** validated. **Question** can the pinned adapter, coordinator and Desktop workflow reproduce the required Claude Code learning and memory outcomes while keeping two remote repositories isolated? Stage a separate research scope before executing the trial.

1. **Establish baseline and provider access.** Pin the actual OpenCode CLI, Desktop and plugin, shared profile, scoped Unimatrix revision and standalone Claude Code binary and hook configuration. Pick one real protocol that delegates work and waits for an owner gate. Run it first on standalone Claude Code and enumerate the required lifecycle and learning signals. In one disposable remote container, pair Desktop, execute a container-only marker, and authenticate ChatGPT and Claude Agent independently with supported flows. Record effective model and credential class and corroborate plan usage with vendor-side evidence. Verify Claude Agent's subprocess cwd and remote login. Use provider-specific evidence and redact account identifiers, credentials and private content.
2. **Compare the same protocol on both OpenCode routes.** Trace accepted prompt, tool outcomes including failure, parent/child lineage and cycle attribution, interrupt/resume and compaction to the intended store. Verify an observable downstream learning or credit outcome and deduplicated recovery across an event-stream interruption. Seed a synthetic memory canary and demonstrate its presence at the model-effective boundary for the first parent, first child and resumed/post-compaction turns. Store a correlation between retrieval, delivery and actual model call. A pre-translation hook or a Unimatrix selection row alone leaves delivery unverified. If provider evidence cannot show delivery, record that route as partial. Exercise provider/model assignment and forbidden child override, unavailable model or quota-class failure, explicit authorized fallback from a known continuation state, and Unimatrix outage. Record attempts and credited effects, including auxiliary model calls. Verify no silent paid fallback or repeated completed side effects.
3. **Prove placement, gate state and isolation in two remote containers.** Use two real repositories, two independently authenticated servers and two approved Unimatrix slugs under one provisioned profile. From one workstation Desktop window, open real files and chat in both, run the same protocol and hold one project at its gate. Record server, canonical checkout, revision, working subpath, container-local tool marker, parent/child sessions and resolved slug per operation. Give each repo a distinct synthetic private canary and confirm positive observation, retrieval and model-visible injection in the correct store and absence in the other. Attempt cross-slug access with a scoped credential and a checkout without a binding. Verify denial or suspension of automatic memory and no writes to the other store. Include a subdirectory or linked worktree and a second clone to test identity assumptions. Disconnect and restart one endpoint, keep the other usable, then reconnect, resume and reconcile events without duplicate credit. Show that the UI marks stale data and derives the blocked gate from durable Issue, artifact and cycle evidence.
4. **Measure enrollment and decide the interface.** Time and count manual steps to enroll a third checkout, including a repeat attempt and any required server restart, without copying shared configuration. Check that a second project remains independently usable and that VS Code can still attach. Keep the Desktop surface if switching and gate inspection satisfy the workflow. A separate console would require a verified server/session handoff. Evaluate Collective publication in a distinct trial with one opt-in provenance-bearing canary only after private controls pass.

**Proof artifact.** Produce a reviewed, redacted invocation and evidence bundle with version manifest, baseline and route-specific request/event analogues, correlation IDs, per-slug assertions, learning/credit outcome, gate/reconnect evidence and a pass/partial/fail table tied to the requirement rows above. The factory validator verifies the bundle against demonstrated behavior. An adapter implementation, screenshots, documentation, selected retrieval text or a successful MCP call alone do not clear the behavioral bar. A route clears only with verified execution in the intended containers, attributable routing, durable observation and use, provider-effective injection and negative isolation controls. Keep adapter candidate #393 at `grade:claimed` until such an artifact is verified and attached.
