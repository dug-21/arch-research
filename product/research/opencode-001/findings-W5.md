# W5 — A consolidated development console with independent project context

**Evidence date** 2026-11-26. **Directional.** OpenCode v2.4.1 (`6f05140`), Unimatrix `e2194af8c32c1fca8767c4e61a0667be4fd7566c`, and owner feedback on issue #77. This is a source audit. The proposed console, onboarding, and protocol paths have no runtime trial.

## Assessment

**Adopt OpenCode Desktop for chat and repository navigation. Assemble a small project registry, enrollment flow and protocol controller around it.** Independent repositories can remain on their own paths and point to distinct stores on one Unimatrix server. A single personally controlled OpenCode server can load shared configuration over many repository locations, and Desktop can also display projects on multiple OpenCode servers. Start by checking whether Desktop plus an experimental status panel or command covers the one-window requirement. Build a small separate dashboard if the required overview cannot be reached comfortably from Home. Neither option needs to reimplement chat, the file viewer, terminal, worktree management, or model providers. [Owner feedback](https://github.com/dug-21/arch-research/issues/77) · [Desktop project state](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/app/src/home/model.ts#L105-L158) · [CLI service model](https://opencode.ai/docs/cli/#background-service)

## Central configuration and repository differences

**Shared configuration source.** Put versioned common OpenCode settings, agent Markdown, command templates, skills and the Unimatrix adapter package in one operator-managed profile. Install or point the OpenCode server's global configuration at that profile. The CLI wires `OPENCODE_CONFIG_DIR` to the server's global config and supports explicit file/content options. The server discovers global, ancestor, repository and system sources per location, so a commonly rooted directory can have centrally managed and repo-local layers simultaneously. Leave durable project instructions and genuinely different requirements with the repository. If multiple machines host OpenCode servers, deploy the same pinned profile to each and track its revision separately from connection state. [Server flags at the pin](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/cli/src/server-process.ts#L114-L138) · [Source discovery](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/config/discovery.ts#L74-L178) · [Agent configuration loader](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/config/plugin/agent.ts#L36-L105)

**Settings versus enforcement.** Global settings act as defaults. Repository/ancestor configuration can contribute settings and extensions. The pinned config assembly gives managed system settings the highest precedence and treats managed policy ordering separately. Connected OpenCode Console integrations can supply settings and higher-priority-than-project policy, but the owner still needs their own registry, Unimatrix enrollment and protocol state. Observe separate policy choices before enabling untrusted project configuration. File access and API credentials need their own boundary. The native file-list API expressly permits browsing outside a requested location, and server password/pairing credentials apply at server scope. A project selected in a UI is a routing convenience. For mutually distrusting execution or console users, use an independently enforced host or server compartment. [Pinned config assembly](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/config.ts#L290-L401) · [OpenCode policy sources](https://opencode.ai/docs/policies/) · [File-list API scope](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/protocol/src/groups/fs.ts#L52-L65) · [Pinned server authentication](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/server/src/auth.ts#L27-L65)

**Per-project overrides.** An experimental `project_overlay` can load an extra folder under the global profile's `project/<opencode-project-id>/`, above repo `.opencode` layers. It is a useful candidate for centrally held OpenCode settings, subject to version testing. The release-channel source tests explicitly enable it. It keys by OpenCode project ID and skips the global ID. W4 shows how separate clones can share that ID, so do not entrust Unimatrix access to the overlay alone. Resolve the running server and canonical checkout against an admitted registry row before choosing the bundle. A shared global OpenCode MCP stanza can point at a project-aware bridge. At this pin a stdio MCP server defaults to the location directory and spawns in the location's execution environment. The bridge still needs to validate its binding there and use a credential available in that environment. One global `UNIMATRIX_BUNDLE` across a multi-project server would bind those locations to the same slug. ## Enrollment and protocol transfer

### Enroll a repository through one explicit operator action

1. Resolve the actual server and Git checkout and show the proposed binding. A project registry row needs an owner-issued stable ID, server/location, repository identity, approved Unimatrix slug, credential reference, profile revision and optional protocol mappings. Branch and worktree are session placement fields.
2. Reuse an existing authorized slug for that repository, or create it on the Unimatrix host. The documented new-slug flow seeds project config and requires a server restart to activate new routing. Show that as an operational step and support retry after restart. Do not create a project based only on a client's guessed directory or remote URL.
3. Keep bundle contents out of application state, prompts, repository files and logs. The project row stores a reference to server-side secret material. Configure model-visible MCP retrieval and trusted adapter observation to use the same slug and verify both actions independently.
4. Run one non-mutating retrieval check and a controlled observation check, verify a wrong-slug denial, and display the observed enrollment state. Repeating enrollment should discover existing rows and reuse valid slug and credentials. A known repo with changed placement should be reviewed before a second checkout is authorized to share its store.

The pinned Unimatrix code documents slug-bound headless credentials and the narrower-access tradeoff. `read` permits retrieval and rejects observation. `read-write` permits observation and grants knowledge-write and session-write capabilities. Keep any wider credential with the adapter, provide a read credential to the model-facing client when only retrieval is needed, and govern curator writes explicitly. A bridge that can observe yet lacks arbitrary knowledge write would need an additional server capability or separately enforced mediation. Legacy bundles have an all-slugs credential. Disabling that credential after migration is a separate rollout check. Unimatrix's existing bundle setup and V1 OpenCode adapter cannot establish v2 automatic retrieval or learning. [Pinned Unimatrix setup and scoped modes](https://github.com/dug-21/unimatrix/blob/e2194af8c32c1fca8767c4e61a0667be4fd7566c/docs/client-setup.md#headless-automation-access) · [Pinned Unimatrix cloud project setup](https://github.com/dug-21/unimatrix/blob/e2194af8c32c1fca8767c4e61a0667be4fd7566c/README.md#serving-projects) · [W3 adapter audit](findings-W3.md)

### Carry protocol content and enforce run transitions

- **Portable content.** Preserve human-readable protocol Markdown as a versioned source and expose it through centrally distributed OpenCode commands or skills. Translate Claude role front matter and native built-in tool names to v2 definitions. Test each model/tool/permission mapping. OpenCode's compatibility loader explicitly scans `.claude/skills` and `.agents/skills`, and its instruction loader falls back to `CLAUDE.md`. That does not make `.claude/agents`, Claude hook configuration, or arbitrary workflow Markdown executable in OpenCode. [Pinned skills compatibility](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/config/plugin/compatibility.ts#L41-L81) · [Instruction fallback](https://opencode.ai/docs/instructions/#claudemd-fallback) · [Pinned OpenCode agent loader](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/config/plugin/agent.ts#L34-L107)
- **Launch.** An OpenCode command can render a template and call a predefined agent/child. For behavior such as a research run, launch through an SDK controller with explicit project, protocol revision, agent, model and permission inputs. The v2 command API enables the same launch action from chat or a console; command implementation may mutate the session choice so use controlled session placement. [Pinned session command API](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/protocol/src/groups/session.ts#L364-L383) · [Pinned command execution](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/core/src/config/plugin/command.ts#L50-L110)
- **Protocol status and gates.** For a garage run, retain the Issue, tracked artifacts, and Unimatrix cycle as authoritative surfaces. Expose their references from a small run index and derive visible phase and gate state from them. A route-specific controller can admit next work through OpenCode only after the required external evidence or owner approval is recorded. Protocol Markdown educates an agent; it does not independently enforce a blocking gate or single-writer role. OpenCode jobs and forms can supply UI signals, but a completed assistant turn does not imply that research coverage, deliverable, or firewall conditions have cleared. [Garage run workflow](../../../.claude/workflow/research-scope.md) · [Pinned OpenCode session and job API groups](https://github.com/anomalyco/opencode/tree/v2.4.1/packages/protocol/src/groups)

## Desktop plugin or thin separate console

1. **Desktop first.** Keep the existing project Home, sessions and files. A GUI extension can list authenticated servers, get each server's synced project/session data and API client, open an enrolled project or prefilled draft, and register commands, settings pages and session-side panels. Its exposed router reports current path and activity. The pinned slots supply a bottom strip and session surfaces, without an explicit Home project-row injection or arbitrary route registration in the inspected GUI API. A command opening a portfolio dialog or a settings page carrying registry/enrollment is a bounded trial. A session-panel view can show protocol/run and memory state after drill-down. Desktop GUI is experimental and version-pin-sensitive. [Pinned GUI server and draft APIs](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/plugin/src/gui/host-apis.ts#L997-L1029) · [Pinned GUI server list](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/plugin/src/gui/host-apis.ts#L1264-L1283) · [Pinned slot and panel registries](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/plugin/src/gui/registries.ts#L879-L978) · [Plugin parts](https://opencode.ai/docs/build/plugins/)
2. **Thin console if the overview needs to be primary.** Build the cross-project list and protocol/status board over a registry, OpenCode's SDK and the provenance sources already used by each protocol. A separate app can supply a full portfolio navigation model and survive Desktop slot changes. It will need a verified handoff to a session, its own authentication for server reads, and reconnect/reconcile logic. Use a narrow backend facade if project-specific users are ever introduced. Keep the execution host within provider credential constraints and use the v2 server adapter for capture and synchronous injection on either UI. [OpenCode SDK and plugin surfaces](https://opencode.ai/docs/build/plugins/) · [Pinned project routes](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/protocol/src/groups/project.ts) · [Pinned file routes](https://github.com/anomalyco/opencode/blob/v2.4.1/packages/protocol/src/groups/fs.ts)
3. **Park shared retrieval until project enrollment and isolation pass.** W4 finds the Collective repository supplies a publication and adoption pattern. A separate approved shared-knowledge lane can use explicitly published, provenance-bearing entries and receiver opt-in. Keep project telemetry and local retrieval distinct. This allows future ideas and reusable decisions to travel without granting a repo-wide query across every Program. [W4 Collective and repository boundaries](findings-W4.md)

## Validation cut

In a two-repository trial, enroll an existing repository and one brand-new repository without copying shared agent, harness or Unimatrix definitions into either. From one desktop window, display project rows and stale states, enter a repository chat, inspect a real file, and launch an existing protocol with an explicit model, known version and gate. Restart the relevant services and reconnect. Show that the scope, protocol stage, active run and memory state derive from durable facts, including an intentionally blocked gate. Run primary and child prompts with separate project canaries, confirm evidence reaches only the correct slug and reproduces the required learning/injection features, then compare how quickly the owner can switch between task modes. Include an attempted reuse of a currently unauthorized clone and a wrong-slug lookup with a scoped credential. The optional shared-memory proof should introduce one published canary only after the private controls pass.
