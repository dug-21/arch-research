## OpenCode V2, native permissions, and Claude Agent

- **Released capability.** OpenCode v2.4.2 shipped 2026-11-26 00:59 UTC. GitHub's release listing includes it while the API's designated latest was v1.19.6, published 2026-11-17. An unqualified installer or GitHub latest lookup cannot establish the V2 version under evaluation. V2.3.0 moved the `subagent` tool to child sessions running asynchronously, with parent notifications and child model choice. Current V2 docs distinguish a primary session's model from a selected agent profile, and let a child inherit the parent's model or use a configured model. Pinned subagent code also accepts an explicit model argument. These are assignment and attribution mechanisms. [V2.4.2 release](https://github.com/anomalyco/opencode/releases/tag/v2.4.2) · [V1.19.6 release](https://github.com/anomalyco/opencode/releases/tag/v1.19.6) · [V2.3.0 release](https://github.com/anomalyco/opencode/releases/tag/v2.3.0) · [Pinned subagent source](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/core/src/tool/plugin/subagent.ts) · [Current agent documentation](https://opencode.ai/docs/agents/)
- **Control counterevidence.** Current documented V2 permissions use individual agent profiles. Custom child permissions use global configuration plus their own rules, with no guarantee of attenuation from their parent's profile. V2 also has hard provider/tool/MCP deny policies and higher-precedence managed or Console policy. The original OpenCode inert-control finding should be read as version-specific. The present ordinary default permits unmatched operations, and the policies govern OpenCode-mediated checks. The v2.4.2 release tightened remembered web approvals for new approvals and fixed visibility of blanket-denied model tools. No reviewed source establishes that native OpenCode child sessions receive distinct OS principals or protected memory credentials. External MCP requests carry an OpenCode session identifier in metadata on the pinned client path. This is useful for correlation. Server-side trust in the caller and attribution of that caller's authority to the child require additional evidence. [V2.4.2 release](https://github.com/anomalyco/opencode/releases/tag/v2.4.2) · [Current permissions](https://opencode.ai/docs/permissions) · [Current policies](https://opencode.ai/docs/policies/) · [Pinned MCP client](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/core/src/mcp/client.ts)
- **Claude Agent path.** OpenCode introduced the installed Claude Code bridge and user login in v2.2.3, 2026-10-30. Anthropic had already announced Sonnet 5.5 and Opus 5.5 in September. The released bridge obtains model choices from the installed CLI/account; exact catalog entitlements and billing remain account-dependent. Relative to the audited v2.4.1 pilot, the query options, provider instruction transform, and subagent source blobs at v2.4.2 are byte-identical by GitHub contents SHA. The Claude bridge therefore still excludes ordinary Claude project hooks via the pinned query options, passes a constrained tool bridge, and uses its provider-specific instruction transform. Current native V2 extension improvements do not establish model-effective arbitrary context injection on the Claude bridge. The same-release MCP client/OAuth changes fix integration signin for URLs bearing query strings. This is separate from subagent custodial identity. [Bridge introduction](https://opencode.ai/changelog/v2.2.3) · [Anthropic model announcements](https://www.anthropic.com/news) · [Query options](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/core/src/plugin/provider/claude-agent/claude/query-options.ts) · [Instruction transform](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/core/src/plugin/provider/claude-agent/instructions.ts) · [Release diff](https://github.com/anomalyco/opencode/compare/v2.4.1...v2.4.2)

## MCP authorization and adjacent enforcement in active projects

- **Released specification.** The MCP authorization endpoint currently resolves to the 2026-07-28 revision. HTTP authorization is optional and has OAuth resource audience binding, current-operation scope challenges and operation-dependent required scopes. The core leaves authorization-server details and the meanings of application scopes to deployments. Official MCP SDK docs describe per-tool enforcement patterns, so a blanket “MCP cannot do per-tool scopes” is too broad. The source record lacks a standard trusted child-principal binding from the harness to the resource server. OAuth authentication of the connection and scope enforcement at the server still need trustworthy assignment of child and project authority. [Dated MCP authorization spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) · [Current MCP PHP SDK authorization](https://php.sdk.modelcontextprotocol.io/run/authorization/)
- **GA incumbent.** GitHub Agentic Workflows left preview on 2026-10-28. GitHub describes read-only by default agent execution, sandbox/firewall, safe output application, dedicated threat detection, optional micro-VM isolation, cross-repository enclaves, and a task-type/difficulty model router. v1.2.2 shipped 2026-11-10. It reuses GitHub Actions policy, and licensing for the default engine remains distinct from repository availability. The evidenced credential boundary is Actions jobs and safe outputs; an arbitrary OpenCode child and an Unimatrix promotion endpoint remain outside that evidence. Evidence does not establish automatic author-declared phase-to-capability derivation. This updates existing #198. [GA announcement](https://github.blog/changelog/2026-10-28-github-agentic-workflows-generally-available/) · [Pinned release](https://github.com/github/gh-aw/releases/tag/v1.2.2)
- **Cold find: sandbox-level scoped identity.** Kubernetes SIGs Agent Sandbox v1.0.12, 2026-11-20, ships sandbox-scoped router tokens and lifecycle/claim support. That is a shipped operational isolation and routing mechanism. It assumes Kubernetes/controller/sandbox operations and authenticates a sandbox-related resource, so credentials for a child sharing that sandbox and authority at an external memory endpoint are separate claims. It provides a stronger source-backed evaluation candidate than a shared-process ID, with materially different infrastructure burden. [Pinned release](https://github.com/kubernetes-sigs/agent-sandbox/releases/tag/v1.0.12)

## By-function sweep — “choose an endpoint from request facts and workload constraints”

vLLM Semantic Router v0.4.0, released 2026-09-27, offers configurable signal-driven routing with local/private/cloud backends. Its current official overview distinguishes policy eligibility checks, heuristic or model-judged signal calculation, selection algorithms, default routing and direct model exposure. The harness retains tool execution and authorization. This is composable routing evidence for HTTP model calls, including an OpenCode-compatible endpoint where the wire contract fits. It does not show that a personal subscription subprocess route can be routed in the same way. A request scorer also cannot certify that routing improved an organizational outcome. Cost includes gateway operations and potentially an extra call for judged signals. Deterministic provider eligibility should be evaluated separately from selection for relative quality, availability, cost, or difficulty. This overlaps the GA GitHub difficulty router at the decision abstraction and differs in placement and credential contract. ## Evidence gaps and coverage

1. **Identity gate:** public source supports host-owned controls and workload-level isolation as mechanisms. The missing composition evidence is a per-child principal bound to an independently governed memory endpoint, with explicit handling of shell access, project binding, credential custody, revocation, and audit. Current OpenCode metadata and configurable agent policy do not settle that claim. This survey cannot render an empirical go/no-go.
2. **Effect boundary:** GitHub's GA is a meaningful delta on the watchlist. Extrapolating it from GitHub effects to Unimatrix or one child within another runtime requires evidence about the custody seam. Ruflo release evidence sharpens provenance and federation leads without settling this boundary.
3. **Provider and model routing:** version, actual runtime, provider/account class, eligible identifiers, tool semantics, fallbacks, and effective context must travel together. Public source cannot verify the owner's account entitlements, usage attribution or application-level quality signal. Exact enterprise pricing and Tem­poral agent plugin GA were outside this scout's verified slice.
4. **Intentional gaps:** no broad patent pass, no maturity verdict for retort/AGNTCY outside sampled repos, no unverified negative about current Claude SDK inheritance, and no experimental validation. Release note labels describe projects' claims, not garage proof.
