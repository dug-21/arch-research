## A1. Bind workload identity to an independently observed execution boundary

**SPIRE 1.16.0, released 2026-11-05.** The pinned Unix attestor documents selectors based on workload UID, group, and optional executable path or hash. The release adds experimental WIT-SVID issuance with TTL controls. These facts describe a workload identity issuer and an experimental token format. Neither gives a verifier a new signal for distinguishing two logical subagents presented as the same workload. A broker or isolated execution boundary must supply the distinction, and a child-exposed bearer credential would still fall within the framing's custody problem. SPIRE involves running an agent and issuer and arranging workload registrations and trust. Existing technology #205 already tracks the SPIRE/Vault minting leg. Flag overlap with active-development findings on sandbox-scoped credentials. [SPIRE 1.16.0 release](https://github.com/spiffe/spire/releases/tag/v1.16.0) · [Pinned Unix attestor](https://github.com/spiffe/spire/blob/v1.16.0/doc/plugin_agent_workloadattestor_unix.md)

**GitHub Actions OIDC, 2026-07-15 rollout.** GitHub issues job tokens and documents issuer-established job/run attributes and immutable owner/repository IDs in the default subject for newer repositories. Legacy repositories retain their prior format unless opted in or renamed/transferred under the rollout. Rechecked the April announcement against the live reference. This supplies a mature precedent for bootstrapping authorization from runtime and repository facts, with job-level granularity. GitHub job identity and GitHub Agentic Workflows safe outputs overlap only at the scheduler boundary, with separate credential custody and effect authorization. [GitHub changelog, 2026-04-23, updated 2026-06-10](https://github.blog/changelog/2026-04-23-immutable-subject-claims-for-github-actions-oidc-tokens/) · [Current OIDC reference](https://docs.github.com/en/actions/reference/security/oidc#immutable-subject-claims)

**OAuth 2.0 Token Exchange, RFC 8693 (2020-01).** A security token service can exchange validated subject and actor tokens for a token scoped by target resource, audience and policy. The JWT actor claim represents delegation. The issuer needs a trustworthy actor input and relying services must enforce the authorization contract. This maps to granular delegation after identity establishment. The old date describes the normative protocol, and the SPIRE release and current GitHub reference were checked for current issuance granularity. [IETF RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html)

## A2. Cold leg — scoped promotion and inherited baselines through TUF

**The Update Framework specification v1.0.37, released 2026-10-08.** Signed, delegated targets metadata can restrict which paths each authorized role may publish. Threshold signatures gate updates. Snapshot metadata binds a coherent set of versions, and timestamp versions and expiry help clients reject rollback and stale metadata. This is a release-distribution analogue for independently authorized promotion and opt-in shared baselines. It carries signer and artifact lineage at release granularity. Source-entry correction chains, consumer-side retraction of cached or injected knowledge, and quarantine semantics remain memory-domain gaps. Its metadata verification incurs signing-key, expiry, and distribution operations. The candidate was outside the theme watchlist and was found by searching release signing, delegated target metadata and rollback protection. Existing #271 is a Git/forge append-only analogue, while TUF concentrates on verifying scoped publication across distribution. ## A3. Audit receipt, append-only integrity and write completeness are different evidence

**Certificate Transparency, RFC 9162 (2021-12), rechecked against Rekor v2.3.0 (released 2026-06-10).** Inclusion proofs bind accepted submissions to a published tree and consistency proofs compare successive views. Certificate Transparency describes the problem of divergent log views and identifies the role of monitors. Rekor v2.3.0 ships tiled transparency logging and hashed entries. Its pinned client specification labels witnessing future, and public checkpoint-witness issue #77 was open when retrieved. This scan did not verify a deployed public witness network. A signed root with a separately operated witness addresses rewrite detection for recorded receipts. Capture completeness requires independent evidence about what should have been recorded. AWS's current CloudTrail documentation provides a separate deployed analogue using service-signed, linked delivery digests, and its reference architecture describes keeping records in a dedicated log archive account. Credible application audit also needs event identity, transaction-to-event linkage, and reconciliation. AWS's transactional outbox reference shows the atomic event/record handoff and the need for idempotent processing when delivery retries. ## A4. Recovery has distinct physical, logical and operational contracts

**PostgreSQL 19.0, GA 2026-11-19.** Versioned official docs confirm base backup plus WAL, point-in-time cluster recovery, and manifest verification. The verifier documentation still calls for a real restore, while the PITR chapter separates logical dumps from WAL replay and notes the handling of external configuration. The analogue supplies mature database-level recovery machinery. Cross-project selective export/import, preservation of correction IDs and provenance, embedding rebuild semantics, and consistency with an independent checkpoint require an application contract. It also adds database and archive operations relative to an embedded store. [PostgreSQL 19.0 release](https://www.postgresql.org/docs/release/19.0/) · [Version 19 PITR](https://www.postgresql.org/docs/19/continuous-archiving.html) · [Version 19 backup verification](https://www.postgresql.org/docs/19/app-pgverifybackup.html)
