## I. Workload identity, authorization and workflow effects

These are directional conjectures. The evidence questions describe the cheapest checks available within this source-only survey.

### I1. Workload-backed child attribution

- **Statement and mechanism.** SPIRE’s workload attestation and Kubernetes Agent Sandbox’s sandbox-scoped routing token could strengthen attribution for a separately isolated OpenCode child. An issuer-established identity ties authority to its observed runtime boundary, and an independent relying service binds that identity to a project and role. Live Unimatrix observation and audit could carry the resulting attribution when the host integration preserves it.
- **Target and class.** Trustworthy project and child attribution at the memory service. **Obvious, step-function.** Cross-domain transplant × security and introspection.
- **Cheapest evidence check.** Seek a pinned OpenCode or integration contract establishing separate sibling principals and identifying what the issuer attests, what the memory service verifies, and who controls access to the authority. A shared runtime principal would leave sibling authority unresolved.
- **Assumption and risk.** A child is launched at an independently observed boundary. Sandbox access tokens may identify only a sandbox router operation, and stronger isolation adds lifecycle and operational cost. [SPIRE 1.16.0, 2026-11-05](https://github.com/spiffe/spire/releases/tag/v1.16.0) · [Agent Sandbox 1.0.12, 2026-11-20](https://github.com/kubernetes-sigs/agent-sandbox/releases/tag/v1.0.12) · [OpenCode V2.4.2 MCP client](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/core/src/mcp/client.ts)

### I2. Delegation evidence accompanies bounded rights

- **Statement and mechanism.** OAuth token exchange and MCP operation-specific scope could preserve which trusted workload delegated an action and which operations the resource server authorizes. A server can apply distinct permissions to project writes, shared reads and promotion based on verified policy and authoritative project binding.
- **Target and class.** Delegated permissions and issuer-backed audit provenance for Unimatrix operations. **Adjacent, incremental once I1 holds.** Minimality × security and introspection.
- **Cheapest evidence check.** Compare the pinned MCP authorization contract, token-exchange semantics and available project-scoped Unimatrix credential path. Seek documentation connecting delegated identity to operation and namespace policy and identifying the revocation contract.
- **Assumption and risk.** Authentication of delegator and delegated actor is established earlier. Standard OAuth claim names do not supply that evidence or establish semantics for parent cancellation and already issued rights. ### I3. Separate proposer and publisher for shared effects

- **Statement and mechanism.** GitHub Agentic Workflows’ safe-output pattern could translate to a project-scoped memory proposer and an independently authorized shared publisher. Proposals retain source and run attribution. A publisher outside the proposing worker’s authority supplies the durable promotion disposition. This could make shared promotion auditable even where many project-writing agents have equally scoped rights.
- **Target and class.** Permissioned cross-project curation and human control over consequential effects. **Adjacent, step-function.** Constraint inversion × human steering and structure.
- **Cheapest evidence check.** Compare the GA safe-output custody contract with existing project-scoped write rights and correction lineage. Seek a source-backed disposition and reconciliation contract linking the triggering proposal, actual accepted publication and later correction. Identify other shared writers that must obey the same authorization policy.
- **Assumption and risk.** Only a trusted publisher can authorize shared promotion. Proposal attribution may remain workload-level, and composition requires defining how published knowledge is corrected or retired at consumers. - **Cheapest evidence check.** Inspect whether the published experimental designs record authority decisions separately from successful task outcomes and distinguish revision, workload and policy context. Compare those observables with the current cycle and observation surface.

### I5. Issuer-established repository identity can simplify bootstrap

- **Statement and mechanism.** GitHub Actions’ issuer-established immutable repository attributes could let Collective enroll projects under a stable identifier and select a versioned shared baseline. - **Target and class.** Low-friction cross-repository onboarding with auditable boundaries. **Non-obvious, incremental.** Scale extrapolation × structure, recovery and cost.
- **Cheapest evidence check.** Read the current OIDC legacy/new repository rules alongside Unimatrix slug enrollment and the OpenCode placement scope. Seek authoritative continuity evidence for rename, transfer and non-GitHub workspaces before treating repository IDs as universally available.
