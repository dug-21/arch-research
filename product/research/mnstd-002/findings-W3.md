**Upstream dependency:** C4.2 is BLOCKED if C2.2 (`file:line` → element) fails. That follows SCOPE's

## 1. How Metanorma users actually work on GitHub

1. **CI = the `actions-mn/*` GitHub Actions** [doc][cfg]. The org lists `setup`, `compile`, `site-gen`,
   `build-and-publish`, `deploy-pages`, `cache`, `release`, `aggregate`, `setup-flavors`, `docker-cli`
   (stale, 2021) and `cli` (stale, 2024). `setup`, `site-gen` and `build-and-publish` were all pushed in
   Oct 2026, so they are actively maintained.
   - `actions-mn/compile@v2` wraps `metanorma compile` (inputs: `input-file`, `type`, `extensions`,
     `output-dir`, `agree-to-terms`, `install-fonts`, `use-bundler`…). It needs metanorma-cli already
     present via `setup`, a gem, or the Docker image.
   - `actions-mn/site-gen@v2` wraps `metanorma site generate` over a `metanorma.yml` manifest, with a
     `strict` input. A documented "Docker Container Usage" job runs in `container: metanorma/metanorma:latest`.
   - `actions-mn/build-and-publish` runs site-gen, uploads a Pages artifact and deploys. Its `destination` is
     `default|gh-pages|artifact`. `actions-mn/deploy-pages` adds **per-PR preview deployments** (on
     `pull_request` opened/synchronize/closed, it cleans the preview on close).
2. **The canonical ISO sample repo `metanorma/mn-samples-iso` compiles on every PR** [cfg][others]. It has
   four workflows, all generated by `metanorma/cimas`, so every Metanorma sample repo shares the pattern:
   - `docker.yml`: on `push: main`, `pull_request` and `workflow_dispatch`, it runs in
     `container: metanorma/metanorma:latest`, executes `actions-mn/build-and-publish@main` with
     `destination: artifact`, then `actions-mn/deploy-pages@v1`.
   - `generate.yml`: the same build on an OS matrix (ubuntu/windows/macos) via `actions-mn/setup@main`.
   - `automerge.yml`: the `metanorma/ci` generic automerge (pascalgn/automerge-action) runs on PR, review and
     check events. In other words, **"merge when checks pass"** is the house pattern.
   - Its `metanorma.yml` manifest lists 44 ISO sources (IS at every stage: np/awi/wd/cd/dis/fdis/prf, plus
     amendment, TR, TS, PAS, guide, directives).
   - **[others]:** PR #130 (`cimas-sync-2026-11-11`) shows `docker` / `generate` / `automerge` runs with
     conclusion `success` on `pull_request`. Example: `generate` run 42946315006. That shows compile-on-PR
     working for others. It does **not** show a broken PR being blocked.
   - Note that the samples pin `:latest`, not a digest. That is the opposite of our N2.1. We must not copy it.
3. **Template repo:** `metanorma/mn-templates-iso` ("Official Metanorma template repository for ISO
   documents", per-doctype dirs, its own `metanorma.yml`) [cfg]. `metanorma new NAME -t iso -d <doctype>
   [-l template]` scaffolds from a "Git hosted remote or local FS template" [probe: `metanorma help new`].
   **Using the remote template would need network access, which breaches N6.1.** The POC should author its
   fictitious draft by hand (N8), or point `-l` at a local copy.
4. **Review on AsciiDoc diffs:** no Metanorma doc describes a PR-line-comment → comment-sheet flow. Three
   searches came up empty (coverage log). The metanorma.org "Reviewing documents" page covers only **in-source**
   reviewer annotations (`[reviewer=…,date=…,from=…,to=…]` + `****`, `TODO`; override
   `:presentation-metadata-render-document-annotations:`) [doc, page last committed 2025-12-07]. That page
   belongs to W4, but it re-confirms mnstd-001's "possibly stale" syntax as current.
   The `workflow.adoc` page says review "is per-SDO" and that **"Often the document will render successful
   despite errors"** [doc]. Our probe confirms this (§3).
5. **The GitHub resolution flow Metanorma does ship is issue-based, not PR-based** [doc: commenter 0.3–0.6
   blog, 2026-08-27]. `commenter github-create` makes one issue per comment. `github-sync` treats the YAML as
   the source of truth and closes dispositioned issues. `github-retrieve` pulls `> **OBSERVATION:**` back
   into the YAML. All three are **forbidden** against live repos (N6.2) and cannot be used offline. The useful
   takeaway is the data model: the YAML stays the single register, and the forge is a projection of it. This
   matches our D6 "one register, two channels" design. Within commenter, a GitHub reference is a
   `github` sub-object on a comment, and the locality is `{line_number, clause, element}` [source:
   `lib/commenter/comment_locality.rb`]. W1 should reuse those field names, and the PR-channel extras should
   sit beside them (§4).
6. **`metanorma site generate [MANIFEST] -o DIR [-x exts] [-S]`** is what CI actually runs [probe: help in
   image; doc: rubydoc metanorma-cli]. The POC gate should use **`metanorma compile` on the single
   document**, which is cheaper, has the same compiler and an identical failure profile. Recording a
   `metanorma.yml` is optional and only for realism. Do not gate on site-gen. It adds collection and Liquid
   steps that no clause asks for.

**What a local simulation must reproduce from the GitHub practice:** (a) one branch per change proposal;
(b) line comments anchored to the diff (path, side, line, commit_id); (c) a required status check that
compiles the PR head in the pinned container; (d) merge only on a green check, with `--no-ff` so the merge
commit exists; (e) nothing leaves the machine.

| Option | Cost | N6 risk | Fidelity | Verdict |

| git-bug (issues in git) | Go binary | low | issue-shaped, not line-on-diff | reject (N2.3, wrong shape) |

The rejections are reasoning from the NFR text plus [doc]. None of them was measured.

**Where review records live.** Keep them outside the document tree so they never enter the v1→v2 source diff.
Otherwise they would create a change that C5.2 cannot attribute. Put them under
`poc/fixtures/reviews/<branch-slug>/<reviewer>.yaml`. That directory plays the "PR UI". An optional realism
mirror is `git notes --ref=review add` on the reviewed commit, which changes no tree. It is not required by
any clause.

## 3. Pre-merge gate (C4.3): measured behavior and recipe

**Probe 1 (the image's exit codes on broken sources).** Image `metanorma/metanorma@sha256:836b7ab2…`
reports Metanorma 2.5.24, metanorma-cli 1.18.6, metanorma-iso 3.5.14 and standoc 3.5.20. It was run with
`--network none`, `-t iso -x xml --no-install-fonts`, on a minimal fictitious ISO draft and five mutations:

| Mutation | exit (plain) | exit (`--strict`) | XML produced | Where the fault shows up |
|---|---|---|---|---|
| good | 0 | 0 | yes | err.html holds severity-1 **style** messages even here (ISO_66, ISO_121) |
| duplicate anchor `[[cl-req]]` | **0** | **0** | yes | stdout `asciidoctor: WARNING … id assigned to section already in use`; err.html `ISO_122 identifier cl-req: duplicate` at severity **1** |
| xref to undefined anchor | **0** | **0** | yes | err.html `ISO_56 cross-reference target … is undefined` at severity 2 only (no asciidoctor line) |
| unterminated `====` block | **0** | **0** | yes | stdout `asciidoctor: WARNING … unterminated example block` only, **not in err.html** |
| unterminated table | **0** | **0** | yes | stdout `asciidoctor: ERROR … dropping cells`; err.html ISO_21 at severity 2 |
| `include::` of a missing file | **1** | **1** | no | `FATAL ERRORS: Unresolved directive …` |

- Severity scale per the source in the image (`metanorma-utils/lib/utils/log.rb`): `0 abort · 1 serious · 2
  not serious · 3 info`. `ISO_122` is declared severity 0 in `metanorma-iso/lib/metanorma/iso/log.rb`, but
  the ISO validation policy (`validation_policy/metanorma.yml`, `ISO_122: severity: error`) **reclassifies** it
  to 1, so a duplicate id no longer aborts. In this build, **`--strict` did not change any exit code.**
- The err.html table carries location, error id, message, context and severity in its last column.
- **Gotcha:** `-o DIR` must already exist. A non-existent output dir raises `Errno::ENOENT` writing
  `*.err.html`, with exit ≠0. If the gate script does not `mkdir -p` first, it fails closed for the wrong reason.
- Timing: one XML-only compile of the minimal doc took about 15 s wall-clock. Budget roughly 3× that for
  html+pdf. This is a measurement, not a benchmark.

**Gate verdict rule (recommended; probe 2 exercised it).** The branch head **FAILS** when any of these holds:
1. compile exit ≠ 0, **or**
2. the expected `document.xml` is missing or empty, **or**
3. stdout carries any `^asciidoctor: (ERROR|WARNING)` line, **or**
4. err.html has a severity-0/1 entry that is **new relative to the base branch's baseline**. Entries are keyed
   on `(severity, error_id, message)`, with UUID-ish `_xxxxxxxx-…` ids normalized.

A plain "any severity ≤ 1" rule would fail the good branch, because of the house-style messages that ISO
injects. Use the baseline diff, or an explicit block-list of ids (ISO_122, the ISO_56 family, any severity 0).
**Record both** in the run report.

**Probe 2 (end to end in a scratch git repo, real compiles):** baseline `main` gave 2 severity-1 style
entries. `change/cl-req-wording` gave **PASS** (exit 0, 0 new severity ≤1 entries, 0 asciidoctor diagnostics).
`change/broken` (seeded duplicate anchor) gave **FAIL** (1 new: `ISO_122`, plus 1 asciidoctor WARNING), and
the guarded merge did not run (`git merge-base --is-ancestor change/broken main`, which returned NO).
**Recommendation for the seeded broken branch:** use the **duplicate anchor**. It is realistic, it is caught by
two independent signals (asciidoctor WARNING and ISO_122), and it exits 0. That proves the gate is not just
`$?`. Optionally add a second seeded branch with a missing `include::`, which the exit code alone catches.

**Gate script design (POC guidance; the probe version is below, trimmed):**

    # gate.sh <repo> <branch> <logdir> -> exit 0 PASS / 1 FAIL; appends one line to <logdir>/gate.tsv
    SHA=$(git -C "$REPO" rev-parse "$BR"); WT=$(mktemp -d)
    git -C "$REPO" worktree add -q --detach "$WT" "$SHA"      # compile exactly the branch head, untouched
    mkdir -p "$WT/_out"                                        # required: -o dir must pre-exist
    docker run --rm --network none -u "$(id -u):$(id -g)" -e HOME=/tmp -v "$WT":/metanorma -w /metanorma \
      metanorma/metanorma@sha256:836b7ab2… metanorma compile -t iso -x xml --no-install-fonts -o _out document.adoc \
      > "$LOG/$N.log" 2>&1; RC=$?
    # err.html → "sev\tid\tmsg" for sev in {0,1}; comm -13 against baseline.sev01; grep asciidoctor diags; test XML
    echo "gate branch=$BR sha=$SHA exit=$RC new_sev01=$SEV asciidoctor_diag=$ADW xml=$XML verdict=$V" >> gate.tsv
    git -C "$REPO" worktree remove --force "$WT"

- Make the **merge wrapper** (`pr-merge.sh <branch> <comment-ids…>`) the only merge path. It runs the gate
  and, only on PASS, runs `git merge --no-ff` with trailers (§4). It also writes a `Gate: PASS <head-sha>`
  trailer. The validator can then check mechanically, for every merge commit M, that `Gate:` sha == `M^2`
  and that gate.tsv holds a PASS line for that sha.
- A `pre-merge-commit` hook is optional realism, and `--no-verify` bypasses it. **Do not rest C4.3 on the
  hook.** Rest it on the wrapper, plus the post-hoc check that `change/broken` is not an ancestor of `main`.
- Do the baseline bootstrap on `main` first. The first gate run on `main` has no baseline, so record it as
  the baseline and not as a verdict. This came up as an artifact in the probe.
- Paths: sanitize `/` in branch names for log filenames. The probe failed closed on this before the fix.

## 4. Review-record schema, normalization, and merge convention

**Review record** (one file per reviewer per change branch). The fields mirror GitHub's
`POST /pulls/{n}/comments` (`commit_id`, `path`, `line`, `side` LEFT|RIGHT, `start_line`, `start_side`,
`body`). Per those docs, `line` is "the line of the blob in the pull request diff", so it must lie inside a
diff hunk [doc]. The record adds the ISO fields.

    review:
      branch: change/cl-req-wording
      base_commit: <sha of main at review time>
      head_commit: <sha reviewed>                 # = GitHub commit_id
      reviewer: {name: "Reviewer Alice", mb_nc: "DE"}
      comments:
        - local_id: 1
          path: document.adoc
          side: RIGHT                             # LEFT = base (v1) blob line, RIGHT = head blob line
          line: 42                                # last line of range (GitHub semantics)
          start_line: 41                          # optional, multi-line
          type: te                                # exactly ge|te|ed (N4.2)
          comment: "…"
          proposed_change: "…"

**Normalization into the C3 register (C4.2).** C4 defines no schema (D6). The normalizer emits **register rows
in W1's schema**, with these PR-channel fields alongside:
`channel: pr`, `source_branch`, `source_commit` (= head_commit), `source_path`, `source_side`,
`source_line`, `v1_line` (the line actually resolved), plus W1's `mb_nc`, `type`, `comment`,
`proposed_change`, `observations` (empty), `clause`, `element_id` (resolved), and the original locator.
Using commenter's `line_number`/`clause`/`element` names for the shared fields keeps N4.1's mapping trivial.

- **Side → v1 line (load-bearing subtlety).** The register anchors are **v1 elements**, but a RIGHT-side line
  number refers to the head blob, not v1. The recommended deterministic mapping comes from
  `git diff -U0 --no-color base...head -- path` hunk headers (`@@ -a,b +c,d @@`):
  - for a LEFT line, or a RIGHT **context** line, the base line number is v1_line, mapped through the hunk offsets;
  - for a RIGHT **added** line, take the nearest preceding base line of the hunk (`a`, or `a-1` when `b=0`).
    The comment then anchors to the v1 element the insertion lands in.
  - Then call **C2.2(`path:v1_line`)** against the v1 build. Record both `source_line` and `v1_line`.
- **Rejections (same as C3.3; exit ≠0, no row enters the register).** Reject in these cases:
  - the `(side,line)` is not inside any hunk (GitHub would refuse it too);
  - C2.2 rejects `v1_line`, for example a document-header line (C2.3's example). **Use this as the seeded
    unresolvable-line negative case**;
  - the type is not in `ge|te|ed`;
  - the comment text or MB/NC is missing;
  - the id is a duplicate.
- **Ids (C3.4 / N5.2):** `PR-<branch-slug>-<reviewer>-<nnn>` or W1's scheme with a channel prefix. Assign
  them deterministically from the file order. Never use a timestamp or UUID (N3.1).
- **Fixture minimum for C4.1:** 2 reviewers × ≥1 line comment each on `change/<slug>`, plus 1 unresolvable
  negative, plus the seeded `change/broken` branch. C5.1 then needs ≥1 PR-channel comment in the disposition
  fixture.

**Merge-commit convention (C4.4).** Use git trailers on a `--no-ff` merge:

    Merge change/cl-req-wording

    Resolves: PR-cl-req-wording-alice-001
    Resolves: SHEET-DE-007
    Gate: PASS 68654bed…

Extraction uses `git log` only. This was measured and returned `id<TAB>merge-sha` per id:

    git log --merges --format='%H%x09%(trailers:key=Resolves,valueonly,separator=%x2C)' \
     | awk -F'\t' '{n=split($2,a,",");for(i=1;i<=n;i++)print a[i]"\t"$1}'

The validator checks that the set of `Resolves:` ids equals the set of register rows with `channel: pr` and
disposition accept/modify (resolved via merge). Rejected PR comments get no merge trailer. **Interplay with
C5.2** (one commit per comment id): give the branch commits a `Comment-Id:` trailer as well, so the
diff-attribution check sees every v1→v2 hunk attributed whether it arrived via merge or via a C5 script commit.
Coordinate this with W2.

**Determinism (N3.1).** Fix `GIT_AUTHOR_NAME/EMAIL/DATE` and `GIT_COMMITTER_*` for every scripted commit and
merge, so that SHAs, and therefore `source_commit` in the register, are identical across runs. This is
expected git behavior, **not yet measured in a two-run diff**, and the POC must demonstrate it. Without it, the
register differs on every run and N3.1 fails.

## 5. N6 / C4.5 check recipe

Measured in the probe:
- `git remote -v | wc -l` returned `0`, and `git config --get-regexp '^remote\.'` returned nothing.
- `git config protocol.allow never` makes `git push <path>` fail with `fatal: transport 'file' not allowed`
  and `git fetch https://…` fail with `fatal: transport 'https' not allowed`.
- A `pre-push` hook that `exit 1`s is a second layer.
- Compiles run with `docker run --network none` (all probe compiles succeeded offline for `-x xml` with
  `--no-install-fonts`; PDF font needs are W0's concern).
- **Honest caveat (measured):** `git -c protocol.allow=always push --no-verify file:///…` **succeeded**. The
  config and hook are guards against accidents, not proof.

C4.5/N6 evidence therefore has to be **(a)** the repo state, **plus (b)** a command trace:
- run the demo under `set -x` / `BASH_XTRACE_FD` to a log, or `strace -f -e trace=connect`;
- the validator greps the trace for `git push|fetch|clone|remote add`, `gh `, `curl|wget`, `commenter github-`
  and `docker pull`, and requires zero hits other than the single declared image pull, if any. The image is
  already local, so the pull is skipped.
- Optional strongest form: run the PR simulation's git in a `--network none` container (the image ships
  `git 2.47.3`). That costs a second git version, so it is not recommended unless the validator asks.

## 6. Flags

- **The gate verdict is the determining constraint for C4.3** (§3). If the POC gates on `$?` alone, the
  realistic broken branch (duplicate anchor) **would merge**. The validator should require the verdict rule to
  be stated, and should require the seeded branch to exit 0 yet still FAIL.
- **`--strict` is inert for this failure class** in cli 1.18.6 [probe]. Do not cite it as the gate mechanism.
- **`git` is not in N1.1's prerequisite list** (Docker, Node 24, Python 3.14). C4 needs host git ≥2.32 for
  `%(trailers:…separator=)`. Host git is 2.55. Either declare git as a prerequisite with a fail-fast check
  (N1.3), or run git inside the image. This is a frontier note for the leader and curator, not a board change.
- **Forge rejection rests on N6.1's literal text** ("only network access is the image pull"). If the owner
  wants real PR UI fidelity, that is an N6.1 amendment, not a W3 call.
- **Side → v1 mapping for RIGHT-added lines** is a design choice (anchor to the insertion point). The
  alternative, resolving against the head build and mapping back via C2.4, is heavier. Flag it to W0/C2.
- Upstream practice pins `:latest` (mn-samples-iso, actions-mn docs). That is the opposite of N2.1. Do not copy it.
- `commenter github-*` exists and is tempting. It must not appear in the command trace (N6.2).

## 8. POC recipe (inputs → commands → expected observable)

1. `git init -b main poc-work/repo`. Fix identity and dates. Set `protocol.allow never`. Install the
   `pre-push` refusal hook. Commit the v1 source. Run `gate.sh main` once to record the baseline.
2. Create `change/<slug>` with ≥1 wording edit. Create `change/broken` with a duplicate `[[anchor]]`.
3. Add `fixtures/reviews/<slug>/{alice,bob}.yaml` (2 MB/NCs, ≥1 line comment each, types from ge|te|ed), plus
   one record on a header line as the negative case.
4. `normalize_pr.py`: hunk-map to v1_line, call the C2.2 resolver, and append to the register. Expect the
   negative to be rejected with its reason, exit ≠0, and absent from the register.
5. `pr-merge.sh change/<slug> <ids…>`: expect `gate … verdict=PASS` and a `--no-ff` merge carrying the
   `Resolves:`/`Gate:` trailers. `pr-merge.sh change/broken`: expect `verdict=FAIL`, no merge, and
   `merge-base --is-ancestor change/broken main` to fail.
6. Evidence: `gate.tsv`, the per-branch compile logs and `.sev01` diffs, the `git log` extraction table,
   `git remote -v` (empty), and the xtrace command log with zero forbidden hits.
